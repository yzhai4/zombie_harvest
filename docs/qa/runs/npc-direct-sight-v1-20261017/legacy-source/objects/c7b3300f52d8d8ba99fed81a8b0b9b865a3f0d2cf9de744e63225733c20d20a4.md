# 尸潮农场扩展接口与内容规范

## 目的

本目录中的武器、支线、NPC 剧情、科技、建筑、势力和据点都采用“数据定义 + 事件账本 + 统一 reducer”的接入方式。内容可以独立启用或停用，不改变昼夜主循环、夜战规则、营地人口守恒和最终尸潮结算。

当前运行时仍以 `dist/index.html` 的现有注册表和命令总线为实现基线。本目录是内容契约，不直接写运行时代码。

## 文件位置与兼容

- 本目录 `剧本/尸潮农场/` 是新增内容的主目录，按主题编号保存，便于后续逐条迭代。
- 已通过实现评审、需要与运行时 `eventId` 对账的正式剧本卡，继续同步一份到 `docs/scripts/<event-id>.md`；该目录是现有工作流和发布记录的兼容入口。
- 同一事件在两处只保留一份规则真相：`剧本/尸潮农场/` 保存完整世界观、分支和视角叙事，`docs/scripts/` 保存实现映射、回放和验收摘要。
- 若两处内容不一致，以最新版本且标注 `contentVersion` 的剧本卡为准；实现提交必须同时引用两个路径（若存在兼容卡）。

## 不可违反的世界规则

- 尸潮农场的黑土菌丝、无线电共鸣、粮食/水源和固定人口是所有新增内容的世界因果根。
- 新 NPC 必须占用固定 roster 名额；剧情不能凭空生成居民。死亡、失踪、重伤和岗位空缺必须可被账本查询。
- 新内容不得绕过 `DAY → NIGHT → SUMMARY → DAY`。夜间只读取白天已提交的准备结果。
- 玩家能改变自治权重和事件结果，但不能把营地自治替换成玩家全知全能的直接控制。
- 所有跨系统改变都通过统一效果操作产生，并写入 `commandId / eventId / causationId`。
- 可选内容不能阻塞主线；NPC 缺席、材料不足、事件过期和玩家跳过都必须有降级结果。

## 注册表和生命周期

| 内容 | 注册表 | 最低字段 | 生命周期钩子 |
| --- | --- | --- | --- |
| 武器 | `WEAPON_DEFS` | `id/family/tags/damage/recipe` | `onCraft/onEquip/onHit/onRepair/onNightEnd` |
| 支线 | `EVENT_CHAIN_DEFS` | `chainId/nodes/startConditions/fallback` | `onDayStart/onChoice/onNightEnd/onExpire` |
| NPC 剧情 | `NPC_STORY_DEFS` | `npcId/storyArcs/requirements/branches` | `onAffinityChange/onJobChange/onDeath/onPromotion` |
| 科技 | `TECH_NODE_DEFS` | `id/branch/cost/prerequisites/unlocks` | `onResearchStart/onResearchComplete` |
| 建筑 | `BUILDING_DEFS` | `id/cost/footprint/slots/hp/coverage` | `onBuild/onDamage/onRepair/onDestroy` |
| 势力 | `FACTION_DEFS` | `id/stance/relations/tradePool` | `onRelationChange/onTrade/onConflict` |
| 据点 | `OUTPOST_DEFS` | `id/capture/requires/garrison/supply` | `onCapture/onGarrisonChange/onLost` |

内容状态只允许通过定义的效果操作改变：

```text
addResource
adjustMeter
modifyRelation
unlockTech
unlockWeapon
scheduleEvent
assignJob
damageBuilding
captureOutpost
recordHistory
```

运行时通过 `window.ZombieHarvestContent` 暴露稳定入口：`register`、`registerPack`、`get`、`all`、`validate`、`applyEffects`、`startChain`、`resolveChain`、`resolveFallback`、`resolveAutonomy` 和 `runHook`。注册同一稳定 ID 会被拒绝；效果批次带 `effectId` 时重复提交只返回幂等结果，批次中任一效果失败会回滚该批次已写入的资源、NPC、建筑和内容状态。

内容存档的默认状态包含 `unlockedTech`、`unlockedWeapons`、`unlockedBlueprints`、`meters`、`scheduledEvents`、`activeChains`、`completedChains`、`outposts` 和 `history`。`unlockTech` 会同时登记科技本身，并把该节点的 `unlocks` 分流到武器或建筑蓝图，后续 UI/建造命令只需读取这些集合。

当前 `CONTENT_SCHEMA_VERSION` 为 1；`migrateContentState` 负责给旧档补齐数组和默认字段。新增状态字段时先提高内容版本，再在该迁移函数中补默认值，并由保存日志记录 `save.migrated`。

事件链的 `phase: ["day_4", "day_10"]` 按最早/最晚日解释；`hooks` 由营地日始、据点夺取等既有生命周期调用。`choice.next` 可进入后续节点，缺席、过期和跳过由 `resolveFallback` 记入世界日志；营地自治通过定义中的 `autonomy.effects` 结算，不会伪装成玩家选择。

效果操作必须可校验、可回放、可幂等。脚本不得直接写 `state`、库存、NPC 生命或建筑耐久；效果失败时记录原因，不产生半套奖励。

## 稳定 ID、版本与保存

- `id` 一经发布永久不复用；显示名称可本地化或改写。
- 内容定义带 `contentVersion`；规则字段变化时递增定义版本并提供迁移函数。
- 保存结构升级递增 `SAVE_VERSION`。旧档缺字段使用安全默认值，迁移结果写入 `save.migrated`。
- 已完成的内容实例以 `instanceId` 标识；重复 dispatch、刷新、回放和加载不能重复扣除或发放。
- 世界日志至少保存：内容 ID、阶段、触发条件摘要、玩家选择、自治结果、效果列表、因果 ID 和降级原因。
- 未启用的可选内容不会改变现有随机种子、夜战预算或主线事件序列。

## 六视角审查

每个新增内容在进入实现前要回答：

1. 玩家：能看到什么局面，选择改变什么，风险是否可理解？
2. NPC：动机、岗位、关系、需求和能力是否支持这项行为？
3. 营地：库存、劳动、建筑占位和人口是否真实支付？
4. 势力：资源、关系和历史记忆是否产生可观察反应？
5. 敌人：尸潮压力、目标、路线或反制是否有因果来源？
6. 全局链：是否影响共鸣度、崩溃值、主线、存档和每日总结？

## 内容扩展流程

1. 先填写对应模板，确定稳定 ID、触发窗口、效果和降级路径。
2. 通过规则/架构评审，确认能映射既有命令总线、事件账本和保存迁移。
3. 注册定义并接入文本、图标、动画和音效资源；表现资源不得改变规则语义。
4. 用固定种子验证成功、失败、缺岗、夜间切换、刷新恢复和重复操作。
5. 将事件日志、六视角审查和静态检查结果回填 `16_扩展内容验收表.md`。


## 实现状态说明

本文件列出的生命周期钩子、据点维护和建筑销毁效果是内容契约；当前运行时已实现稳定注册、效果校验、事务回滚、基础据点守军槽位校验和建筑 HP 变更，但完整 `onGarrisonChange/onLost/onDamage/onDestroy` 以及重复派驻/upkeep 结算属于 v83 开发任务。内容作者不得据此跳过交接状态标记。

## 内容包挂载与存档

内容定义/注册清单属于启动配置，不写入存档；存档只保存 `contentState` 和内容版本。加载旧档前必须按启动配置重新 `registerPack` 并校验版本；缺包时进入安全降级（不执行缺失链、不发放奖励），写入 `content.pack.missing`，不得把缺失定义当作完成节点。
