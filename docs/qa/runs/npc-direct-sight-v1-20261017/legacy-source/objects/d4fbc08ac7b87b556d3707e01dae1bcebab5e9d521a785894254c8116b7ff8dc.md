# 引擎迁移门槛

当前生产入口是 Sites v76 的静态 Web 版本，GitHub main 还包含兼容性修正。暂不迁移重型引擎。

## 继续现有路线的条件

- 事件树、NPC 状态树、夜战、存档仍能通过模块化 JavaScript 和回归脚本维护。
- 主要瓶颈是规则正确性与内容生产，而不是渲染性能。
- Web 入口仍能保持移动端触摸、桌面输入和存档兼容。

## 触发迁移评估

同时满足以下至少三项时，重新比较 Cocos、团结或其他可直接验证的引擎：

- 需要可视化编辑大量地图、动画、碰撞和时间线。
- 单文件拆分后仍有跨系统改动，回归成本高于功能开发成本。
- 需要稳定的资源导入、图集、骨骼动画和多平台构建流水线。
- Web 与微信小游戏、原生包需要共享同一套内容和运行时。
- 真机性能测试显示当前 Canvas/DOM 路线无法达到目标帧率。

## 迁移前置

1. 冻结事件、存档和 NPC 状态的数据契约。
2. 为 renderer、input、storage、clock、event queue 建立接口。
3. 先做一个可回退的战斗场景垂直切片。
4. 用旧存档、移动端和桌面端回归通过后，再迁移主线。

迁移不能以“代码更现代”为理由启动；必须由可量化的内容生产、性能或平台需求触发。
