## 结论

这是**公开探索策略把不可达可见目标当唯一目标**造成的方法终态，不是已证明的游戏寻路／碰撞bug。当前方法缺少“先筛当前已观察可达区域，再选探索边界；目标不可达时换其它公开边界”的逻辑。

## 公开证据与失败机制

- 初始`001-initial-map-ui.json`：61个公开可见且命中测试通过的tiles，x2–12/y5–12，SHA `bd324f56e8ee5b11c51035a0d02bb419ae7e2f508b7b748b22af8d0d7051f46a`。
- 最终`002-final-ui.json`：115个公开tiles，x9–26/y5–12，SHA `9cb8e56a868489797624ac6258a7ad73f62647d2a27f734d4adcbbb0721d377c`。
- 已目视`002-final.png`（SHA `dca06d71f77a7468ba2757837963c8b4e74a263994a41abc9cb1a3f798b71d27`）：水带分隔画面左右，右侧远端中继台可见，但当前公开地形未暴露绕行连接；下方仍有未观察区域。这里“看见地块”不等于“已知走得到”。
- `exploreGoal`75–82只把passable且距玩家>1.1的已知tiles按最大x排序；优先条件仅为东邻尚未知。它**没有检查BFS可达性**。`navigate`59–60在第一个目标无公开路径时即返回failed；unknown分支157把它提升为整个执行终态。
- 仅以已存初始＋最终公开tiles做离线图计算（没有执行游戏）：上述排序选(26,11)“远端中继台”所在边界；从公开终点取整起点可达的已知分量最多到x20，无法抵达该目标1.01范围，x21/y5–11为已观察水面。因此公开材料足以重现这一失败机制。中间每次完整view未归档，最终目标／path也未写入decision；这不是对每一帧内部known集合的精确重放，不能伪称已证明实际唯一选中节点。
- 动作26–38在约x17、y10.6–11来回改向，均有位移。每轮重新选目标、取整网格起点和短脉冲会带来折返；这是效率风险，但**此次终态直接原因是无路径即全局停止**，不是三次碰撞阈值。

## 最小方法修正

1. 对当前已观察地图先做一次从玩家所在格出发的可达分量计算，再从该分量选择探索边界；边界应允许四向任一未知邻接，而不只东邻。east-first可保留为平局偏好，不能优先越过已知水带选不可达点。
2. 可见但暂不可达的地标保留为“待连接”的公开记忆；尝试其它可达探索边界，只有所有可达边界均已耗尽／既定导航预算到限时才报信息或导航不足。不要从真坐标补一条隐形路线，也不硬编码水带缺口。
3. 短段动作之间保留当前公开waypoint，直到到达、碰撞或新公开目标出现才重选，减少取整与目标变化导致的折返；无需新通用导航框架。
4. 决策加小型证据：当前goal坐标及其公开观察来源、可达节点数、选用边界方向、拒绝理由。只保存已有公开信息，不加truth导航字段。这样下一轮失败可直接归因，无需推断未保存的known集合。

这只修探索方法，不保证A下一次一定找到广播塔／存活／online。原A01字节与失败终态保留，新driver另冻身份；不把本复核当新玩法执行。
